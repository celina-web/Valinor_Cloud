❯ Como paso siguiente, quiero desarrollar el plan completo (tanto Backend como  
  Frontend) para implementar la utilización de la tecnología WebSocket          
  (utilizando la librería Socket.io) con el fin de crear un chat en tiempo real 
  en la aplicación. Este chat permitirá que los usuarios con rol "recepcion" o  
  "profesional" inicien una conversación con un usuario "admin" para realizar   
  consultas.                                                                    
                                                                                
  Para estructurar la solución de manera robusta y profesional, el diseño debe  
  cumplir estrictamente con las siguientes reglas de negocio, arquitectura y    
  UI/UX:                                                                        
                                                                                
  1. Restricciones de roles:                                                    
     - El usuario con rol "admin" NO puede iniciar una conversación. Su rol es  
  reactivo: recibir, aceptar, rechazar o finalizar chats.                       
     - No puede haber chats entre usuarios administradores entre sí. Las        
  conversaciones son exclusivamente Admin-Recepción o Admin-Profesional.        
                                                                                
  2. Ciclo de vida y estados del chat (State Machine):                          
     Cada chat debe manejar explícitamente estados en el backend: PENDIENTE     
  (esperando aceptación), ACTIVO (conversación bidireccional), FINALIZADO       
  (cerrado por el admin o por timeout) y RECHAZADO.                             
                                                                                
  3. Flujo de apertura y moderación:                                            
     - Cuando un usuario (recepción o profesional) abre el chat, se crea la     
  solicitud con un mensaje inicial y se pone en estado PENDIENTE.               
     - El usuario NO puede enviar más mensajes hasta que un administrador       
  acepte la conversación.                                                       
     - El flujo esperado es: Usuario envía consulta inicial > El sistema busca  
  un Admin disponible y le notifica > Admin acepta el chat > El chat pasa a     
  estado ACTIVO y se habilita la mensajería bidireccional.                      
                                                                                
  4. Timeout por inactividad inicial (5 minutos):                               
     - Controlado estrictamente desde el BACKEND: si transcurren 5 minutos      
  desde que un usuario (recepción/profesional) inició un chat en estado         
  PENDIENTE y ningún admin lo aceptó, el servidor debe expirar el chat, cambiar 
  su estado a FINALIZADO/TIMEOUT y notificar al cliente para que deba generar   
  una nueva solicitud.                                                          
                                                                                
  5. Enrutamiento y disponibilidad de Administradores:                          
     - El servidor debe llevar un registro en memoria de las conexiones de      
  Socket.io de los administradores activos.                                     
     - Cuando se inicia un chat, este debe despacharse únicamente a un (1)      
  administrador conectado (puedes aplicar una estrategia de selección aleatoria 
  o al primero de la lista).                                                    
     - Si no hay ningún administrador conectado en ese exacto momento, el       
  sistema debe rechazar la apertura del chat y responderle al usuario con el    
  aviso: "Todos los operadores se encuentran ocupados en este momento".         
                                                                                
  6. Finalización de la conversación:                                           
     - El administrador puede dar por finalizada la conversación en cualquier   
  momento.                                                                      
     - Al hacerlo, el backend cambia el estado a FINALIZADO, emite un evento de 
  aviso al otro usuario bloqueando la interfaz de chat, y la conversación ya    
  no permite el envío de nuevos mensajes. Para volver a consultar, el usuario   
  deberá iniciar un nuevo chat.                                                 
                                                                                
  7. Especificaciones de Interfaz de Usuario (Frontend / UI / UX):              
     - Ubicación del acceso: Al lado del icono de usuario (situado a la derecha 
  de la navbar), agregar un **ícono de mensajes / chat** con un badge           
  indicador si hay chats activos o pendientes.                                  
     - Componente visual (Slide-over Drawer): Al hacer clic en el ícono de      
  mensajes, debe desplegarse un panel lateral deslizante desde la derecha de la 
  pantalla (un cajón o *drawer* flotante) que aloje la interfaz del chat, sin   
  bloquear el resto de la vista principal.                                      
     - Interfaz adaptada por roles:                                             
       * Para Recepción / Profesional: Una vista limpia para iniciar consulta,  
  ver el estado de espera (PENDIENTE), el chat activo (ACTIVO) con burbujas de  
  mensajes, o la opción de iniciar un nuevo chat si fue finalizado.             
       * Para Administrador: Una sección o lista de chats entrantes pendientes  
  de aceptación, la posibilidad de aceptar/rechazar, y la interfaz para chatear 
  y finalizar la conversación de forma dinámica en tiempo real usando           
  Socket.io.                                                                    
                                                                                
  Por favor, analiza la arquitectura completa (eventos de Socket.io,            
  almacenamiento temporal o en DB, manejo de salas/rooms, estructura de         
  archivos frontend con Tailwind/Pug y cliente de socket.io) y genera el plan   
  detallado para su implementación.

     Plan: chat de consultas en tiempo real (Socket.io) — TurnoFlex

     Contexto

     Los usuarios recepcion y profesional necesitan consultar a un administrador
     sin salir de la app. Se agrega un chat 1 a 1 (usuario → admin) con estados
     explícitos (pendiente, activo, finalizado, rechazado), asignación a un
     único admin conectado, timeout de 5 minutos controlado por el servidor y un
     drawer lateral en la navbar.

     Decisiones tomadas:
     - Híbrido REST + Socket.io. Todas las acciones (iniciar, aceptar, rechazar,
       finalizar, enviar mensaje) son endpoints /api/chats. Así reusan
       requiereLogin → requierePermiso → controlador, tomarCampos, errorHandler,
       auditoría y Postman, y renuevan la cookie JWT. Socket.io queda para
       empujar eventos del servidor al cliente (y para registrar qué admins
       están conectados).
     - Límite por admin configurable (CHAT_MAX_POR_ADMIN, por defecto 3). Se
       elige el admin conectado con menos chats pendiente+activo; si hay empate,
       al azar. Si no hay admins conectados, o todos están en el límite, la API
       responde 503 con "Todos los operadores se encuentran ocupados en este 
       momento" y no crea el chat.
     - La persistencia va en MongoDB (modelo Chat con los mensajes embebidos)
       para tener historial, poder recuperarse si se reinicia el servidor y que
       la carga de cada admin se cuente desde la base. En memoria quedan solo la
       presencia de los admins y los timers.
     - Reglas de la app multipágina: cada navegación cierra y vuelve a abrir el
       socket. Por eso:
       a. Los eventos se emiten a salas por usuario (usuario:<id>) y no a salas
          por chat. Así no hay que reincorporar a nadie a las salas, y funciona
          igual con varias pestañas abiertas.
       b. Un admin se considera desconectado recién después de un período de 
          gracia (10 s) sin sockets abiertos.
       c. Al cargar cada página, el estado se lee por REST.

     Backend

     Dependencia y arranque

     - npm install socket.io (v4). El cliente se sirve solo en
       /socket.io/socket.io.js y no hace falta CDN. En Docker: docker compose up
       --build -V.
     - src/index.js: reemplazar app.listen por const server = 
       http.createServer(app); iniciarSocket(server); server.listen(PORT). En
       iniciar(), después de conectarDB(), llamar a recuperarTimeouts().
     - .env.example: CHAT_MAX_POR_ADMIN=3, CHAT_TIMEOUT_MINUTOS=5 (variable
       opcional que sirve para probar con 1 minuto).

     Modelo src/models/Chat.js

     ESTADOS = ["pendiente", "activo", "finalizado", "rechazado"]
     MOTIVOS_CIERRE = ["admin", "timeout", "rechazo"]
     solicitante: ObjectId ref Usuario (required)
     rolSolicitante: "recepcion" | "profesional"
     admin: ObjectId ref Usuario (asignado; cambia si se reasigna)
     estado: enum ESTADOS, default "pendiente"
     motivoCierre: enum MOTIVOS_CIERRE, default null
     expiraEl: Date            // creación + CHAT_TIMEOUT_MINUTOS (solo tiene 
     sentido en pendiente)
     aceptadoEl, cerradoEl: Date
     mensajes: [{ autor: ObjectId ref Usuario, texto: String trim 1..1000, 
     createdAt }]
     timestamps: true
     Índices:
     - { admin: 1, estado: 1 } para calcular la carga de cada admin.
     - { estado: 1, expiraEl: 1 } para recuperar los timeouts.
     - Índice único parcial { solicitante: 1 } con partialFilterExpression: { 
       estado: { $in: ["pendiente","activo"] } } (Mongo 7 lo soporta). Garantiza
       un solo chat abierto por usuario; si choca, el errorHandler ya
       devuelve 409.

     Exportar ESTADOS y ABIERTOS como hace Auditoria.ACCIONES.

     Máquina de estados — src/services/chatService.js (carpeta nueva)

     Tiene toda la lógica de negocio y la usan los controladores, los handlers
     del socket y los timers. Cada transición es un findOneAndUpdate atómico con
     el estado de origen en el filtro, para que no haya carreras entre
     "aceptar" y "timeout":

     ┌────────────────┬───────────────────────────────────────┬────────────────┐
     │   Transición   │                Filtro                 │     Quién      │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ crear →        │ (no hay otro chat abierto)            │ solicitante    │
     │ pendiente      │                                       │ (no admin)     │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ pendiente →    │ {_id, estado:"pendiente", admin: yo}  │ admin asignado │
     │ activo         │                                       │                │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ pendiente →    │                                       │                │
     │ rechazado      │ ídem                                  │ admin asignado │
     │ (motivo        │                                       │                │
     │ rechazo)       │                                       │                │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ pendiente →    │                                       │                │
     │ finalizado     │ {_id, estado:"pendiente"}             │ timer del      │
     │ (motivo        │                                       │ servidor       │
     │ timeout)       │                                       │                │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ activo →       │                                       │                │
     │ finalizado     │ {_id, estado:"activo", admin: yo}     │ admin asignado │
     │ (motivo admin) │                                       │                │
     ├────────────────┼───────────────────────────────────────┼────────────────┤
     │ agregar        │ {_id, estado:"activo",                │ ambos          │
     │ mensaje        │ $or:[{solicitante:yo},{admin:yo}]}    │ participantes  │
     │ ($push)        │                                       │                │
     └────────────────┴───────────────────────────────────────┴────────────────┘

     Si el update devuelve null, se responde 409 con un mensaje claro (por
     ejemplo "El chat ya no está pendiente"). Los estados finalizado y rechazado
     son finales.

     Funciones:
     - iniciarChat(usuario, texto):
       a. Verifica que no tenga un chat abierto (409).
       b. Llama a elegirAdmin(); si devuelve null, lanza un error de status 503
          con el mensaje de operadores ocupados.
       c. Crea el chat con el mensaje inicial en mensajes[0].
       d. Llama a programarTimeout(chat).
       e. Emite chat:nuevo al admin y chat:actualizado al solicitante.

       Toda la asignación corre dentro de un mutex en proceso (una cadena de
       promesas encolar(fn)), para que dos solicitudes simultáneas no superen el
       límite.
     - elegirAdmin({ excluir }):
       a. Toma los ids conectados desde presencia.adminsConectados().
       b. Calcula la carga con Chat.aggregate (match admin ∈ ids, estado ∈ 
          ABIERTOS, group por admin).
       c. Descarta los que tienen carga ≥ CHAT_MAX_POR_ADMIN y elige el de menor
          carga (desempate aleatorio).
     - aceptar, rechazar, finalizar y enviarMensaje emiten el evento
       correspondiente a los dos participantes. aceptar y rechazar cancelan el
       timer.
     - expirar(chatId) lo llama el timer. Hace la transición a
       finalizado/timeout, emite chat:finalizado a ambos y audita como
       "sistema".
     - reasignarPendientesDe(adminId): cuando un admin se desconecta, mueve sus
       chats pendiente a otro admin disponible (emite chat:retirado al anterior
       y chat:nuevo al nuevo). Si no hay ninguno disponible, quedan pendientes
       hasta el timeout.
     - asignarHuerfanos(adminId): cuando un admin se conecta, le asigna los
       chats pendientes cuyo admin está desconectado, hasta llegar a su límite.

     Timers — src/services/chatTimeouts.js

     - Map<chatId, Timeout>: programar(chat) usa setTimeout(expirar, expiraEl - 
       now) y cancelar(chatId) lo limpia.
     - recuperarTimeouts() al arrancar: los chats pendiente con expiraEl <= now
       se expiran ya mismo (sin socket para emitir, se corrige solo cuando el
       cliente vuelva a leer por REST) y al resto se le reprograma el timer. Así
       el timeout de 5 minutos sobrevive a reinicios o a recargas de nodemon.

     Socket.io — src/socket/index.js

     - iniciarSocket(server) crea new Server(server) (mismo origen, sin CORS) y
       exporta emitirA(usuarioIds, evento, datos) → io.to(ids.map(id => 
       "usuario:" + id)).emit(...), además de desconectarUsuario(id) →
       io.in("usuario:"+id).disconnectSockets(true).
     - Autenticación en el handshake, reusando el código existente:
       - io.engine.use(cookieParser())
       - io.engine.use(...): solo en el handshake (req._query.sid === undefined)
         llama a autenticar("jwt", req, res) de src/middlewares/auth.js. Si no
         hay usuario, responde 401; si lo hay, guarda req.usuario.
       - Un io.use copia socket.request.usuario a socket.data.usuario, y también
         exp, que sale de info.payload.
       - Así el socket hereda la verificación de firma, tokenVersion, activo y
         expiraEl sin duplicar lógica.
     - connection:
       - El socket se une a usuario:<id>.
       - Si el rol es admin: presencia.conectar(id, socket.id) y después
         asignarHuerfanos(id).
       - El socket no recibe comandos (por la decisión del modo híbrido). El
         único evento cliente→servidor opcional es chat:escribiendo {chatId}: se
         reenvía al otro participante después de validar que el socket es parte
         de un chat activo. Si se quiere menos alcance, se deja para después.
     - disconnect: si es admin, llama a presencia.desconectar(id, socket.id).
     - Sesión larga: con un setInterval por socket (o al recibir cada evento) se
       compara socket.data.exp con la hora actual; si venció, se llama a
       socket.disconnect(true). La siguiente navegación o fetch reautentica.

     Presencia de admins — src/socket/presencia.js

     - Map<adminId, Set<socketId>> más Map<adminId, Timeout> de gracia.
     - conectar: agrega el socket y cancela la gracia pendiente.
     - desconectar: saca el socket; si el Set queda vacío, arranca la gracia de
       10 s. Al vencer, borra al admin y llama a
       chatService.reasignarPendientesDe(id).
     - adminsConectados() incluye a los que están dentro del período de gracia,
       porque solo están navegando entre páginas.
     - Limitación documentada: es un solo proceso de Node. Para escalar
       horizontalmente harían falta @socket.io/redis-adapter y presencia en
       Redis, y eso queda fuera de alcance.

     Revocación del socket

     - authController.logout: después del $inc tokenVersion, llamar a
       desconectarUsuario(req.usuario._id).
     - usuariosController: hacer lo mismo cuando se desactiva un usuario, se le
       cambia el rol, se le pone un vencimiento, se le cambia la contraseña o se
       lo elimina.
     - Si era admin, el disconnect dispara la gracia y después la reasignación.

     Permisos — src/config/roles.js

     - profesional agrega "chat:usar" (lo heredan recepcion y admin por el
       spread).
     - admin agrega "chat:moderar".
     - Siguiendo la convención de control por contexto, iniciarChat rechaza con
       403 a un usuario admin ("Los administradores no pueden iniciar
       conversaciones"). Con eso tampoco pueden existir chats entre admins: el
       único que puede iniciar nunca es admin, y el asignado siempre lo es.

  Cómo funciona
  - Acciones por la API y avisos por el socket: iniciar, aceptar, rechazar,
    finalizar y enviar mensaje son endpoints /api/chats, con los mismos
    middlewares, auditoría y errores que el resto. Socket.io solo avisa en
    tiempo real a los dos participantes.
  - Estados: pendiente → activo → finalizado, o rechazado. Si dos acciones
    chocan (por ejemplo, el admin acepta justo cuando vence el plazo), gana una
    y la otra recibe 409.
  - Asignación: cada consulta va a un solo admin conectado, el que tiene menos
    chats abiertos, con un tope configurable (CHAT_MAX_POR_ADMIN, por
    defecto 3). Si no hay ninguno libre, responde 503 con "Todos los operadores
    se encuentran ocupados en este momento" y queda auditado.
  - Plazo de 5 minutos: lo controla el servidor y se mantiene aunque el servidor
    se reinicie.
  - Admin que se desconecta: como la app es multipágina, el socket se reconecta
    en cada cambio de página. Por eso un admin sigue contando como conectado
    durante 10 segundos de gracia. Si no vuelve, sus consultas pendientes pasan
    a otro admin.
  - Seguridad del socket: usa el mismo JWT que la API. El logout, desactivar a
    un usuario o cambiarle el rol le cierran el socket al instante.
  - Interfaz: ícono de mensajes con badge al lado del avatar y un panel que
    entra desde la derecha sin bloquear la página. Cambia según el rol, sigue
    abierto al navegar entre páginas y funciona en móvil.
